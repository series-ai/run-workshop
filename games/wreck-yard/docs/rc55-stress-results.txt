rc.55 stability and performance tests
====================================

Date: 19-20 October 2026, Pacific time.
Source: 8593239561ac9b6e144919718e70ba3feb27893b.
SDK: published 6.0.0-rc.55, git cf8edf558cc565edbef81cfab9dd64f7e7a71432.
Control: published 6.0.0-rc.54.

The tests used an isolated checkout with an actual copy of the published SDK.
They did not use the local solver experiments. The main project dependency
stayed unchanged. Timed native and browser tests ran in sequence.

Body-count boundary
-------------------

Ten touching boxes and a floor pass with 16 total bodies on rc.55. Maximum
displacement is 0.007931 m. Add one distant static body with collisions
disabled, and maximum displacement becomes 12.289766 m. Colliding body IDs
and order stay fixed. Both worlds replay exactly and release native resources.
The rc.54 control fails both world sizes.

The published solver selects new contact behavior with bodyCount <= 16 and
proxyHook == nullptr. See core/native/physics/physics.cpp near lines 5157,
10024, 10098, and 10279. This guard excludes the dense yard scene.

Run the portable check from games/wreck-yard:

  node scripts/repro-syncplay-body-count.mjs --sdk /path/to/rc55/package --out test-results/body-count-new.json --require-stable

The strict check returns exit 1 on the published rc.55 package.

Dense recovery
--------------

A public-API fixture creates 400 touching boxes in 40 columns of ten tiers.
It wakes them once at frame 121. At frame 2520, after 2400 neutral ticks,
372 bodies remain active. Maximum displacement reaches 13.263102 m.
The rc.54 and rc.55 motion traces are identical. Both retain finite state,
replay exactly, and release tracked native resources.

The fixture fails our displacement and recovery gates. The 0.05 m gate is
derived from the existing ten-box test. It is not a documented SDK guarantee
for every physical arrangement. Persistent activity and collapse are separate
observations. The long horizon is 80 simulated seconds after the wake.

Topology edit
-------------

At frame 240 in the dense fixture, replace one top box. Change its X half-size
from 0.48 m to 0.47 m. Preserve its current pose, velocity, mass, and inertia.
Both releases fail with:

  physics.edit-failed: KINETIX_NATIVE_WORLD_OPERATION_FAILED: apply topology batch: status -8: topology edit peak bound was below the allocation

The rc.55 control fails with and without a retained checkpoint. Releasing the
checkpoint does not make a retry succeed. Digest, motion, frame, body count,
and shape remain unchanged after failure. Disposal releases tracked native
resources. The wrong forecast term has not been isolated.

Run:

  node scripts/repro-syncplay-topology-bound.mjs --sdk /path/to/rc55/package --out test-results/topology-new.json --require-success

The strict check returns exit 1 on the published rc.55 package.

Performance comparison
----------------------

The existing contact probe ran in official rc.54, rc.55, rc.55, rc.54 order.
Each used a separate process and the same fixture. Public step plus output
read times in milliseconds were:

  Version/run   Rest p50/p95     Shove p50/p95
  rc.54 A       3.548 / 4.592    15.436 / 17.291
  rc.55 B       3.286 / 4.268    14.147 / 16.138
  rc.55 B       3.320 / 4.212    14.261 / 16.531
  rc.54 A       3.618 / 4.852    14.083 / 16.437

The active timings overlap. These runs do not establish a general speed gain
or phone frame budget. They include public API and output work, not only the
native solver. Contact rows do not count active solver constraints.

App tests and memory
--------------------

Build, identity check, and TypeScript passed. The full suite passed 538 of
539 tests across 74 files. One cage test expects a sky-shot miss, but its ray
starts inside portal A. It receives blocked on both rc.54 and rc.55. No fixture
or app source was changed for these tests.

The storage profile and stable/busy runner retention profiles reached 600
frames. Storage tested four players. Retention tested one player. They kept
256 logical saves and at most 32 retained native captures. Old-state replay
and encoded state matched exactly. Owned native slots, worlds, and retained
bytes returned to zero after disposal.

Storage measurements:

  Peak raw JS physics history       227070676 bytes, 216.55 MiB
  Native retained high-water        28634472 bytes, 27.31 MiB
  Process RSS high-water            807321600 bytes, about 770 MiB
  Tick including capture p50/p90    24.078 / 28.740 ms
  Capture/conversion p50/p90        1.473 / 1.656 ms

These are separate metrics. They must not be added as independent memory
totals. Raw physics buffers exclude game state and garbage. RSS includes the
process. The scripts do not measure total allocation counts or post-dispose
JavaScript reclamation. Bounded high retention is not a demonstrated leak.
The 600-frame profiles cover 20 simulated seconds. They do not prove a phone
memory or frame-time budget.

Browser tests
-------------

The existing three multiplayer cases passed: startup, URL join, code copy,
peer movement, interpolation, leave/rejoin, invalid-code retry, recovery, and
room switching. The first movement case observed about 58-60 rendered Hz and
29.2 confirmed Hz. These are frame sequences, not native solver-step counts.

A controlled 6x CPU slowdown for six seconds caused a long recovery gap.
At one aligned wall-second, the host authority was at tick1439, while the
client sent inputs for ticks432-533. It processed105 confirmations in that
second, all with its own input substituted. Public ready stayed true while
about900frames behind. The first run accumulated30.5s of rollback work.

A short reverse-path check ruled out a wall as the only explanation. After
CPU rate returned to normal, reverse movement was zero on both peers. The
frame gap took27.671s to recover. Real movement worked on both peers afterward.
That run accumulated24.1s of resimulation and1398 own-input substitutions.
The slowdown is artificial. It proves a recovery failure under that load,
not its frequency on a physical phone.

The130s room test received a valid snapshot at tick3600/sessionFrame3601.
Its departure took30.578s; rejoin took10.417s. No snapshot rejection appeared
in this rc.55 server log. The exact-target donor defect remains in source;
this successful transfer does not cover a missing target checkpoint.

Corrected Chrome touch and WebKit smoke checks passed. Chrome was155.0.8059.85;
WebKit was26.6. Both received the actual rc.55 session identity. Chrome used a
390x844 mobile layout and real CDP touch movement/release. WebKit used complete
native taps, pause/resume, and frame advance. A neutral state after a short Jet
tap proves release only, not sampled active flight. Neither is phone proof.

Original mobile attempts incorrectly required the desktop-only Live lamp.
The first correction read the controller before it existed. Those failed
attempts remain in the evidence. Final readiness waits for the real live Move
pad before controller reads. Desktop assertions were preserved. Final two-case
run passed2/2 in5.9s. A wrong-depth temporary TypeScript config also failed;
final tsconfig.final.json uses explicit clean paths and passed.

The existing real-touch storage-torch drive passed6checks and10segments:
protocol calibration, real route,10s heldCut with cuts/fractures, release, and
60s settling. There were no page, shader, or session errors. Its performance
still failed to return to baseline:

  Phase             Display Hz   Pump p95 ms   Native step+read p95 ms   Active p50
  Idle10s           59.97        8.70          6.50                      2
  HeldCut10s        35.38        61.56         29.60                     410
  Final50-60s       48.68        25.90         23.63                     507

Native body count increased697->706->802. Render body count increased
544->553->649. Torch cuts stayed19 after release; fractures increased3->35.
This confirms persistent activity and cost after the actual cut ends. The
public native phase includes output work. It is not pure solver time. Trace
rings did not overwrite records. JS heap includes profiler retention. WASM
memory was not reported by this browser trace. No leak claim follows.

App source review
-----------------

Two independent session agents review the app delta and official SDK.
No P0/P1 production API flaw is found. No new public physics call is needed.
The stack-crate material has friction 0.85 and a registered native name.
Storage and returns crates keep wood appearance, hit sounds and break rules.
Their fragments retain storageBay and therefore keep the contact material.
The fuel-drum fixture now places the player relative to the drum's actual
resting position. Its blast assertions remain. The vehicle test covers 24
small pose offsets and retains travel greater than 3 m and scrap speed below
12 m/s. The final full suite passes all 539 tests.

One review issue needed a test correction. The target reduced the storage
motion gates from 0.24/0.096 m to 0.06/0.01 m for bottom/top layers, but still
counted vertical movement. The corrected test first runs a no-shove control
from a settled checkpoint. It then restores that checkpoint and applies the
same shove. Both layer checks require horizontal movement beyond the initial
and control positions. Vertical settling cannot satisfy the gates.

The first correction incorrectly required positive Z motion. That full run
passed 538/539. A three-arm diagnostic resolves the failure: neutral bodies
stay still; wake-only top bodies settle about 2.4 mm; with the shove, median
bottom Z moves +87.96 mm and top Z moves -15.75 mm, with about +5 mm top Y.
The top response is real horizontal motion in the opposite direction.
The final check uses horizontal magnitude and keeps the target distance gates.
The full final suite passes 539/539. The first failure is a test assumption,
not an observed SDK regression. All diagnostic inputs and results remain.

Existing unrelated cage and checkpoint test corrections remain separate.
The cage ray correction is present in the tested working-tree source. This
report does not attribute that old fixture correction to rc.66.

Memory and changed retention policy
-----------------------------------

The runner default is now snapshotRetention 'required'. Offline retains the
current save. Networked clients retain prediction/rollback frames and checksum
or donation frames. The app has no arbitrary old confirmed-frame reads.
The README now identifies rc.66 and the actual default policy.

The profiler previously required 256 logical/32 native saves for every run.
It now tests the default separately from explicit --window full history:

  Policy             Drive     Logical/native retained   Native peak
  default-required   stable    1 / 1                     2
  default-required   busy      1 / 1                     2
  window             stable    256 / 32                  32
  window             busy      256 / 32                  32

All four drives reach frame 600 and dispose to zero. This is an offline
runner test. It does not prove networked retention or donation by itself.

The separate manual 256-save four-player storage drive also reaches frame
600. Old-state decode, replay, checksum and encoded output match. Raw JS
physics history peaks at 173293530 bytes, 165.27 MiB. Native retained
high-water is 19437128 bytes. These metrics overlap and must not be added.
The manual fixture deliberately keeps old saves; it does not measure the
new default runner policy. Tick including capture p50/p90 is 3.243/7.748 ms;
capture/conversion is 0.837/0.962 ms. This is one sample, not an ABBA claim
or a phone budget. Native ownership returns to zero.

API and coverage limits
-----------------------

Source inspection shows no <=16-dynamic solver cutoff. Supported contacts
have a minimum of 16 iterations and cylinder contacts 24. The snapshot
versions, physics ABI and 160 MiB native ceiling remain. Contact chunks can
share unchanged checkpoint data. Wheel support and portal tracking change.
The real-WASM app suite covers the existing vehicle and portal fixtures;
that suite is not proof for every wheel, portal or shape arrangement.

maxConfirmedFramesPerTurn is available but opt-in. This integration keeps
the other AI runner settings. It does not claim a bounded confirmation-work
budget. A successful stall test cannot establish a worst-case scheduling
bound. Missing-target donor refusal/rotation and hosted account behavior
remain separate coverage limits. Local desktop tests are not iPhone proof.

Capacity and presence
---------------------

A room has four fixed simulation slots. Solo has one. A join or leave must
not resize state.players, renumber slots, or recreate the physics world.
The crew display must count people separately from slot capacity.

The public runner reports confirmed presence per slot:

  human        Occupied by a person.
  substituted  Occupied. The authority substituted a missing input packet.
  empty        No person occupies this slot.
  unknown      Confirmed presence is not available yet.

Human and substituted both count as occupied. Unknown is not empty.
Transport occupancy can supply a display fallback while confirmed presence
is unknown. It is room metadata, not a deterministic game input.

The runner's slot array supplies capacity when available. Before that array
arrives, use transport maxPlayers, then the authored maximum. Game SDK 5.28's
local WebSocket server omits maxPlayers from room:joined. Its client defaults
to one despite a four-seat authority. This affects room metadata. The native
session and runner slot array retain the correct four-slot capacity. The local
server must include maxPlayers, players, and creator status in its join reply.

The local display correction exposes crew.occupied and crew.capacity through
MatchSnapshot. It updates the existing Crew label. Solo shows 1/1. A four-seat
room with one confirmed human shows 1/4. A missing packet does not reduce it.
The display correction does not change the simulation or hide player bodies.

Authority policy
----------------

The rc.54 default retains a departed owner's seat claim:

  recycleVacatedSeats: false
  allowHumanClaimBot: false
  onHumanLeave: empty
  initialBotSlots: []

For a yard with reusable human seats, the intended policy is:

  recycleVacatedSeats: true
  allowHumanClaimBot: false
  onHumanLeave: empty
  initialBotSlots: []

Worker NPCs are separate from player seats. Do not add workers to initialBotSlots.

The supported configuration path is rundot/realtime.config.json. Its shape is:

  {
    "rooms": [{
      "type": "deterministic",
      "config": { "maxPlayers": 4, "playerCount": 4 },
      "deterministic": {
        "seatPolicy": {
          "recycleVacatedSeats": true,
          "allowHumanClaimBot": false,
          "onHumanLeave": "empty",
          "initialBotSlots": []
        }
      }
    }]
  }

The installed Game SDK 5.28 Vite plugin reads this file and derives server
rooms configuration. A rundot/rooms.config.json file can override that value,
but it takes a bare array. The wrapped realtime config also serves the local
sidecar. Adding seatPolicy to yardRoomOptions does not activate it: the rc.54
browser helper neither accepts nor forwards that field.

The game now declares the deterministic room type in rundot/realtime.config.json.
It does not set an explicit seat policy. No server policy was deployed by this
audit. The deployed implementation and policy were not verified. Do not enable recycling
and describe the game integration as complete until canonical cleanup passes.

Remaining SDK boundary
----------------------

The authority records occupiedSlots and checksums its input frames. The rc.54
network client supplies only decoded inputs and game commands to a custom
runtime. The installed adapter callback is step(inputs, commands). Seat intents
stay in the authority. The runner exposes latest confirmed presence afterward.

Latest presence is suitable for the crew display. It cannot drive YardSim.
It lacks the ordered frame history and owner identity required by replay.
Canonical null is also not a complete ownership contract. A neutral input is
not proof that a person left. A new owner can take the same slot without an
observable empty simulation frame.

A complete integration needs a public ordered seat event or per-tick seat
context. Include slot, effective frame, control kind, and a control epoch or
claim identity. Save and replay it. Reconcile predictions when it changes.

SDK change locations in the published package:

- dist/authority-room.js records the confirmed occupiedSlots data.
- dist/networked-client.js sends decoded inputs and commands to the runtime.
- core/runtime.d.ts defines the adapter step(inputs, commands) contract.
- dist/runner.d.ts exposes latest presence after confirmed stepping.

SDK acceptance checks must cover join, leave, same-tick owner replacement,
retained-owner reconnect, late join, snapshot restore, and replay. Compare
canonical checksums after restore and replay. Exercise prediction through a
seat transition. Missing input substitution must retain the same seat owner.
Do not require the game to infer identity from occupancy or input values.

The game must then reconcile that event before player actions:

- Release gravity holds and torch state.
- Clear jetpack, velocity, feedback, and button-edge state.
- Release driving and make the buggy available.
- Skip empty players in movement, actions, storage guards, and lift riders.
- Hide empty slots from avatars, beams, effects, and audio.
- Start a new owner with fresh player state.
- Stop interpolation across an owner or epoch change.
- Preserve position for a retained-owner reconnect under the chosen policy.

Current neutral input releases grab and torch. It does not clear ridingVehicle.
Storage guards and lift updates still inspect all fixed players. Presentation
still projects all fixed slots. These are unresolved game integration gaps.
Do not hide the avatars alone: that would leave invisible simulation blockers.

Verification
------------

The 1.8.1 local built-artifact check found an intentional-leave delay. The
client left at once. The other client's crew count changed from 2/4 to 1/4
after 30.6 seconds. Its simulation continued during that time. This result
does not prove the timing of a hosted room.

Game SDK 5.28's public ServerRoom.leave() closes the socket. Syncplay's
transport.close() calls that method. The room server treats socket closure
as a disconnect and keeps membership during reconnect grace. No supported
public operation removes membership at once. The deprecated RoomsV1 API
belongs to another room system and must not be used for this purpose.

The SDK needs an explicit intentional-leave message. That message must remove
membership before socket closure. Unexpected disconnects must retain their
reconnect grace. No SDK or server policy changed during this check.

Multiplayer session flow
------------------------

Each game launch creates a multiplayer room. Pause shows the current code and
a Copy code button. The code remains selectable if clipboard access fails.
The Join another room field accepts typed or pasted codes. Joining leaves the
current room. An empty code and the current room code cannot be submitted.
Pause blocks local input while the authority continues. Product menus and
error recovery do not offer solo play. Offline mode remains in MatchController
for native simulation tools and tests.

The controller closes transports returned by a superseded start. This prevents
a room seat leak during React StrictMode startup and repeated room requests.
The real-authority regression checks cover stop, restart, and network pause.

The session change passed 24 real-authority/controller checks, 29 gate checks,
and seven browser tests. Chrome and WebKit desktop plus Chrome touch layouts
passed the pause, code, resume, and input checks. Real clipboard copy/paste
and a two-player room join passed. An injected browser clipboard rejection
verified the manual-copy UI. Native clipboard-denial behavior in RUN remains
unverified. No page errors occurred in the feature checks.

The existing vista brightness check still fails. A controlled comparison
gave both multiplayer and the old solo startup behavior a median luma of 35.3
and dark fraction of 0.173. The limits are 40 and 0.12. Camera pose, viewport,
and fonts matched. This session change did not cause that brightness failure.

Use scripts/serve-local-multiplayer.mjs for local checks. The standard browser
test configuration starts it. The vista test also uses that local server.
It does not start a separate authenticated playground server.
